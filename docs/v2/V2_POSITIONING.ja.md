受容済み P0 実装／ギャップ分析記録: [`V2_P0_EXECUTION_SAFETY.md`](V2_P0_EXECUTION_SAFETY.md)。最終 V2 コアには、明示的で権威ある操作台帳、所有者／世代フェンス、耐久性のあるデスクトップ隔離、エビデンスを伴うレシート、明示的解決、固定セットマルチデバイス不変条件の証明、バックエンド移植性、信頼された実 Cua 物理受容が含まれます。

この文書は、V2-M1 受容後および最終競合レビュー後の V2 の製品境界を定義します。境界は意図的に「安全なリモートコンピュータ利用」、「ベンダーニュートラルなデバイス制御基盤」、「マルチマシン MCP」よりも狭くされています。

## ポジショニング

`computer-use-mcp-gateway` V2 は、**状態付きインタラクティブデスクトップの委任制御に対する不確実性考慮型実行安全レイヤー**です。

短い製品ステートメントは以下のとおりです:

> 認可はエージェントが行動できるかどうかを決定します。CUMG はさらに、デスクトップ操作の所有者が誰であるかを決定し、副作用が不確実になった場合に推測を拒否します。

CUMG は、単に以下の点において差別化を主張するものではありません:

- ベンダーニュートラルであること;
- 委任認可または能力トークンシステムであること;
- 物理デバイスまたはフリート制御基盤であること;
- コンピュータ利用エンジンまたはスクリーンショット／入力実装であること;
- AI ネイティブなリモートデスクトップ製品であること;
- 汎用 MCP ゲートウェイであること;
- 汎用能力ブローカーであること;
- デバイスレジストリ、予約サービス、またはマルチマシンルーターであること。

これらの領域にはすでに相当な OSS と標準のカバレッジがあります。SINT Protocol や Arm Device Connect などのプロジェクトは、より広範な「ベンダーニュートラル物理デバイス実行／ガバナンス」カテゴリに実質的に重複しています。一方、OpenClaw、OAHL、QuickDesk、Obot、および委任認可プロジェクトは、追加の近接レイヤーをカバーしています。

最終レビューでは、特に関連性の高い実行安全リファレンスも2つ発見しました:

- **ROSClaw** は、エンボディードエージェントに対する密接に関連した物理実行契約をすでに実装しています: 正確な許可、エージェントセッション、有限デッドライン、排他的リソース／ボディリース、耐久性のあるアクション遷移、リスタートリカバリ、中断された実アクションのリカバリ、オペレーター確認、世代無力化、古い物理アクションのリプレイ／再開なし。
- **Agent libOS** は、密接に関連した耐久性のある外部エフェクトセマンティクスを提供します: プロバイダ実行前に意図を永続化、副作用境界前に権威を消費／予約、曖昧な失敗後に `unknown` エフェクトを保持、リスタートにわたる重複／リプレイされた決済を防止。

したがって、CUMG はリース／リカバリ／リプレイなし、または耐久性のある曖昧エフェクト理論が独自であると主張してはなりません。防御可能な境界は、これらのクラスの安全セマンティクスの**インタラクティブデスクトップ特化と統合**です: 実行結果が曖昧になった場合の、共有デスクトップセッション上の状態変更操作に対する排他的所有権とフェールクローズリカバリ。

## コアシナリオ

コア問題は以下のシーケンスです:

```text
external principal
      |
      v
specific interactive desktop
      |
      v
exact capability
      |
      v
exclusive operation ownership + fencing
      |
      v
state-changing action
(click / type / drag / process / other effect)
      |
      v
cancel / timeout / disconnect / lost response
      |
      v
can non-execution or termination be proven?
      |
  +---+---+
  |       |
 yes      no
  |       |
terminal  indeterminate
          |
          v
      device quarantine
          |
          v
    explicit resolution
```

曖昧な操作は、クライアント、Hub、エージェント、トランスポート、またはバックエンドが再接続しただけで自動的にリプレイされることはありません。

## CUMG の所有物

### 1. 物理操作アイデンティティと所有権

すべての状態変更デスクトップアクションには、明示的な操作アイデンティティと権威ある所有者が必要です。

CUMG の所有物:

- 明示的な操作 ID;
- デバイスごとの操作准入と排他的所有権;
- 世代／フェンスチェック;
- 競合するデスクトップアクションのシリアライゼーション;
- 所有権を静かに転移できないリスタート／リカバリルール;
- 操作世代を所有していない古いエージェント／セッション結果の拒否。

### 2. 曖昧な副作用状態

キャンセルリクエスト、切断、タイムアウト、または応答喪失は、クリック、ドラッグ、キーストローク、プロセス、またはその他の状態変更エフェクトが実行されなかったことを証明しません。

非実行または終了を証明できない場合、CUMG は成功または失敗を推測する代わりに、`indeterminate` 結果を永続化しなければなりません。

`indeterminate` は通常のトランスポートエラーではありません。耐久性のある実行状態です。

### 3. フェールクローズ隔離と明示的リカバリ

曖昧な状態変更作業について、CUMG の所有物:

- リプレイ拒否;
- リスタート安全な曖昧インフライト状態;
- デバイス隔離;
- 影響を受けるデスクトップを再利用する前の明示的解決;
- リスタート／リ接続にわたる曖昧な操作アイデンティティの保持;
- リ接続、フェイルオーバー、またはクライアントリトライ後の自動リプレイなし。

解決パスは、生存性や新しい接続から安全性を推測するのではなく、安全性判断を明示的に行わなければなりません。

### 4. 正確な実行境界

外部認可は、ローカルな実行問題に還元されます:

```text
principal -> stable desktop -> exact DeviceCapability
```

CUMG は、MCP Authorization/OAuth、OIDC、IAM ライクシステム、SINT スタイル能力システム、Grantex/Open Agent Auth クラスプロトコル、またはその他の維持管理されている認可ソースを消費できます。認証自体は CUMG の製品ロジックではありません: 外部アイデンティティシステムまたはレビュー済みの認証エッジが呼び出し元を証明し、ノースバウンドアダプターはその証明を `AuthenticatedClientPrincipal { issuer, subject }` に還元します。

CUMG の認可はその還元の後に開始します。`DeviceCapabilityAuthorizer` は、その認証済みプリンシパルが1つの安定したデスクトップを1つの正確な `DeviceCapability` に使用できるかどうかにのみ答えます。アイデンティティストレージ、パスワード／セッション処理、トークン発行、汎用アカウント管理は CUMG の外部に留まります。したがって、自己完結型署名 JWT はアイデンティティを確立するために CUMG ユーザーデータベースを必要としません; 認可ストレージは別個の関心事です。

ランタイムは RFC 7662 OAuth イントロスペクションと、意図的にシングルプリンシパルなデプロイメントに対する信頼された認証プロキシ固定プリンシパルアダプターをサポートしています。OIDC/JWT は、Firebase/Auth0/Cognito/Entra/Keycloak などのプロバイダに対する望ましい汎用署名トークン方向のままです。信頼されたプロキシアダプターはループバックオリジンを必要とし、プリンシパルアイデンティティをオペレーター設定からのみ取得し、クライアントアイデンティティヘッダーを信頼しません; マルチプリンシパルポリシーには改ざん防止された認証アイデンティティが必要です。

ノースバウンドクレデンシャルはエージェントクレデンシャルではなく、デバイススコープ実行付与の代替としてサウスバウンドに転送してはなりません。カスタム価値は、別の汎用認可プロトコルを発明することではありません。認可された意図を上記の操作所有権ステートマシンにバインドすることです。

### 5. バックエンド中立の実行エビデンス

Cua は最初の GUI／コンピュータ利用バックエンドであり、製品境界ではありません。

ネイティブプラットフォームアダプター、OpenClaw ベースの実行、またはその他の実装は、コアステートマシンを弱めることなく、操作をサポートされているターミナル／曖昧な結果の1つにマッピングするために十分なエビデンスを提供できる場合は、統合できます。

バックエンドはクリーンな終了を証明し、隔離を回避できます。できない場合、CUMG は保守的に留まります。

## 設計再利用ポリシー

CUMG は**無関係な製品スコープを継承せずに、実証された実行安全のアイデアを再利用すべき**です。

### ROSClaw

ROSClaw を、デフォルトでフォークするコードベースではなく、物理的所有権とリカバリセマンティクスの主要リファレンスとして扱います。

概念的マッピングは意図的にレビューされています:

| CUMG | ROSClaw 対応物 |
| --- | --- |
| デスクトップ／デバイス | ボディ／リソース |
| `DeviceCapability` | 能力 / 正確な許可スコープ |
| 操作 ID | アクション ID |
| 操作所有者 / プリンシパルセッション | エージェントセッション / アクター |
| デスクトップリース | アクション／リソース／ボディリース |
| 世代フェンス | デーモン世代 / DISARMED リカバリ境界 |
| リプレイバリア | 冪等性 + 古いアクション ID リプレイなし |
| `indeterminate` | 未知の結果を伴う中断された REAL アクション |
| 隔離 | リカバリ必要 / DISARMED 物理境界 |
| 明示的解決 | オペレーター `acknowledge-recovery` |
| 結果エビデンス | `ExecutionReceipt` |

CUMG ステートマシンを変更する前に、提案されたセマンティクスを ROSClaw と比較し、インタラクティブデスクトップに適合する場合、より強力な挙動を採用します。

デスクトップボディを追加するために ROSClaw を長期フォークし**ません**。ROSClaw は、CUMG の意図的に狭いスコープの外にあるロボット／ランタイム／サンドボックス／メモリ／チームの関心を含む、より広範なエンボディードエージェント OS に進化しています。その製品サーフェスをインポートせずに分離できる場合は、将来の互換性実験や `DesktopBody`／アダプター proof が歓迎されます。

### Agent libOS

Agent libOS を、耐久性のある曖昧な外部エフェクト会計のリファレンスとして扱います: エフェクト境界前に意図を永続化、ディスパッチ前に権威を予約／消費、クラッシュ／リスタートにわたる未知のエフェクトを保持、重複決済からファイナライゼーションを保護。

CUMG は、デスクトップ操作ステートマシンを強化する場合にこれらの不変条件を借用すべきですが、未解決の曖昧な GUI 操作が競合するプリンシパルから共有インタラクティブセッションを隔離できるという追加のデスクトップレベル要件を保持します。

## 保持 ／ 適応 ／ 廃止 ／ 再利用

### 保持: プロジェクト所有のコア

不確実性考慮型デスクトップ実行安全を直接エンコードする場合のみ、カスタムセマンティクスを保持します:

- 明示的な操作アイデンティティ;
- デスクトップごとの排他的操作所有権;
- 所有権を保持するために必要なリース／フェンス／世代セマンティクス;
- 古い結果の拒否;
- 状態変更操作に対するリプレイバリア;
- 耐久性のある `indeterminate` 状態;
- 隔離と明示的解決;
- 曖昧な状態変更作業の自動リプレイなし;
- 要求されたキャンセルと、証明された非実行または証明された終了を区別するキャンセルセマンティクス;
- 隱密性を保護する操作／ポリシー／結果エビデンス。

### 適応: 交換可能を保持

後で交換される可能性がある既存の実装周りのインターフェースを保持します:

- プリンシパル／認証アダプター;
- 付与発行者と検証者;
- エージェント／ワークロードアイデンティティプロバイダと検証者;
- Hub-Agent トランスポートバインディング;
- ポリシーエンジン統合;
- 持続化／チェックポイントストア;
- デバイスレジストリ／フリートプロバイダ;
- バックエンドアダプター。

### 廃止または置換

既に存在するという理由だけでカスタムインフラストラクチャを保持しません。同等の挙動がコア不変条件を弱めることなく証明できる場合は、維持管理されている標準または OSS を優先します。

候補には以下のものが含まれます:

- MCP Authorization / OAuth / OIDC;
- 汎用委任認可プロトコルまたは能力トークンシステム;
- 汎用物理デバイスディスカバリ／レジストリ／ファブリックレイヤー;
- TLS と証明書ライフサイクル;
- スケールが正当化する場合の SPIFFE などのワークロードアイデンティティ;
- OpenTelemetry/OTLP;
- OS サービス監視;
- 汎用ポリシーエンジン;
- 汎用フリートルーティングコンポーネント。

置換は、回帰エビデンスが CUMG の実行安全不変条件が保持または改善されることを示した後にのみ受け入れられます。

2026-08-13 の P2 レビューと具体的な採用決定は [`V2_P2_REPLACEMENT_SEAMS.md`](V2_P2_REPLACEMENT_SEAMS.md) に記録されています。これは狭い認可とコンピュータ利用バックエンドのシームを追加しますが、外部依存や新しい制御基盤は追加しません。

### 外部の再利用

CUMG は、重複するサーフェスを再実装する代わりに、維持管理されている OSS を消費または統合する意思を持つべきです。

監視すべき重要なプロジェクト／カテゴリには以下のものが含まれます:

- **ROSClaw** — 物的所有権、排他的リース、中断アクションリカバリ、リスーム／リプレイなしセマンティクスの最も近いリファレンス;
- **Agent libOS** — 耐久性のある未知の外部エフェクトと保護されたクラッシュ後決済の最も近いリファレンス;
- **SINT Protocol** — 能力トークン、物理 AI ガバナンス、アクションアイデンティティ／リプレイ／エビデンス、エッジ権威;
- **Arm Device Connect** — ベンダーニュートラル物理デバイスディスカバリ、アイデンティティ、レジストリ、ACL、マルチテナント状態、エージェント／デバイス接続;
- **OpenClaw** — エージェントランタイム、ペアリングノード、コンピュータ利用実行;
- **OAHL** — ハードウェア能力抽象化とデバイス予約;
- **QuickDesk** — リモートコンピュータ利用とマルチデバイス／フリート UX;
- **Obot** — アイデンティティ、MCP ガバナンス、ワークステーション登録、監査;
- **Grantex / Open Agent Auth クラスシステム** — 委任認可。

外部コンポーネントが CUMG の不確実性考慮型実行コアの外に留まる場合は、統合が優先されます。

## コア優先実行優先度

将来の実行順序は意図的に**コア優先**です。

### 優先度 0 — リファレンスモデルギャップ分析

**P0 ハーディングパスで完了済み; [`V2_P0_EXECUTION_SAFETY.md`](V2_P0_EXECUTION_SAFETY.md) を参照。** レビュー済みルールは: 将来のステートマシン変更の前に、ROSClaw のアクション／セッション／許可／リース／リカバリ／レシートモデルと Agent libOS の外部エフェクト持続化／ファイナライゼーションモデルに対して1対1の比較を実行すること。

- CUMG がすでに一致するセマンティクスを特定;
- デスクトップに適合する場合、より強力な実証済みセマンティクスを採用;
- 意図的に逸脱するのではなく、デスクトップ固有の逸脱を明示的に文書化;
- 無関係なエンボディードエージェント／ランタイムスコープをフォークまたはインポートしない;
- 将来の互換性／アダプター実験を可能に保つ。

### 優先度 1 — 操作ステートマシンの堅牢化

- 操作所有権遷移を明示的かつ網羅的にテスト;
- ターミナル `completed`、`failed`、または証明されたキャンセル結果に十分なエビデンスを定義;
- 不確実な遷移をトランスポート形状のエラーではなく、耐久性のある `indeterminate` に収束;
- 所有権世代変更後の遅延／古い結果を拒否。

### 優先度 2 — 隔離と解決をファーストクラスに

- 接続／セッション寿命に関係なく隔離を独立して永続化;
- 明示的で監査可能な解決パスを公開;
- 解決者が解決している曖昧な操作を特定することを要求;
- 解決が古い操作のリプレイを誤って認可しないことを確認;
- 隔離と解決の両方中にリスタート／クラッシュをテスト。

### 優先度 3 — リ接続／リスタート／同時実行下での所有権の証明

- 競合するプリンシパルはインフライト／曖昧な操作を盗んだり継承したりできない;
- リ接続は古い作業に対して新しい所有者を作成しない;
- Hub／エージェントリスタートは必要なフェンスと曖昧性状態を保持;
- 古いエージェント世代は古い操作をファイナライズできない。

### 優先度 4 — マルチデバイス証明、フリート製品作業ではなく

上記のステートマシンが強力になった後にのみ、以下を証明します:

1. デバイス A は曖昧なアクション後も隔離されたままにできる。
2. デバイス B は別の認可されたプリンシパルによって独立して使用可能なまま。
3. 2番目のプリンシパルは明示的解決までデバイス A を取得できない。
4. Hub リスタートは両デバイスの独立した状態を保持。
5. リ接続／フェイルオーバーはデバイス A の曖昧なアクションを決してリプレイしない。

これらの不変条件がパスする前に、フリート UX、広範なディスカバリ、ダッシュボード、またはオーケストレーションを優先しません。

### 優先度 5 — バックエンド移植性の証明

コアが意図的に Cua 固有でないことを証明するために、材料的に異なるキャンセル／結果挙動を持つ少なくとも2つ目の実行バックエンド、または決定論的なリファレンスバックエンドを統合します。

バックエンドは CUMG ステートマシンに適応すべきであり、CUMG ステートマシンはバックエンドに合わせて弱体化してはなりません。

## 将来のサブシステムに対する決定ルール

新しいサブシステムを実装する前に、以下の順序で質問します:

1. これはデスクトップ操作所有権、曖昧性処理、隔離、明示的解決、またはリプレイなし安全を直接強化するか？
2. はいの場合、コア優先作業です。
3. いいえの場合、関心事は維持管理されている標準、プラットフォーム、または OSS によってすでに所有されているか？
4. はいの場合、並行実装を構築するのではなく統合または置換します。
5. 外部ソースが適合しない場合、カスタムセマンティクスを必要とする正確な実行安全プロパティを文書化し、カスタムサーフェスを狭く、バックエンド中立、トランスポート中立に保ちます。

## GO / NO-GO ルール

**GO:** インタラクティブデスクトップの委任制御に対する不確実性考慮型実行安全を改善し証明します。

**デフォルト NO-GO:** これらの機能が技術的に可能であるという理由だけで、汎用エージェント認可プロトコル、汎用物理デバイスファブリック、汎用フリートマネージャー、リモートデスクトップ製品、またはマルチマシンルーターを構築します。

将来、別の維持管理されている OSS が同等のデスクトップごとの操作所有権、フェンス、耐久性のある `indeterminate` 隔離、明示的解決、自動リプレイなしセマンティクスを提供した場合は、埋没コストを防衛するのではなく、統合または廃止を再評価します。

### P1 証明ステータス — 固定セット構成のみ

P1 証明は、P0 操作ステートマシンを変更せずに、優先度 4 と 5 が要求する最小構成を実装します。`FixedMultiDeviceHub` は、明示的にプロビジョニングされた安定したデバイス ID から既存の `SingleDeviceHub` サービス／ハンドルへの不変マップで、デバイスごとに異なるチェックポイントディレクトリを持ちます。これはデバイスディスカバリ、フリートレジストリ、共有スケジューラー、または製品ルーティング基盤ではありません。

この証明は、デバイス A が1つのプリンシパルの下で耐久性のある隔離されたまま、デバイス B が別のプリンシパルの下でネイティブシェル作業を継続できることを示します。A のリ接続は A の世代のみを進め、A のパーティションは B をブロックせず、Hub 再構築は2つのチェックポイントを独立して復元し、古い曖昧な A 操作が自動的にリプレイされることはありません。古い／誤った所有者の決済は、変更されていない P0 フェンスによって拒否されます。

バックエンド移植性は、Cua と材料的に異なるキャンセル／結果契約を持つ決定論的なプロセスライクリファレンスエグゼキュータによって証明されます。証明された未開始／クリーン終了は既存のターミナルエビデンスクラスにマッピングでき、証明不能なコミット後の結果は `indeterminate` にマッピングされます。同じ操作アイデンティティ、所有者、世代、隔離、明示的解決、レシート、リプレイなしコアが両バックエンドに使用されます。

P1 物理受容は 2026-08-13 に、デスクトップ E2E 実行 `31675515516` の信頼された `main` コミット `bb39390f3587902a7df918fe1ff4a8b28c328d50` に対して完了しました。実 Cua レーンは、曖昧性 -> 耐久性のある隔離 -> Hub／エージェントリスタートと世代進捗（リプレイなし） -> 正確な明示的解決 -> 安全な再利用を証明しました。ワークフローはマニュアルのまま、`main` のみで、一時的な TCC 付与 macOS ランナーで実行されました。これにより、P1 残留がクローズされ、P1 をフリートやバックエンド製品作業に拡大することはありません。
